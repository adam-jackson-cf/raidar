# Benchmark Web App UX Review

Date: 2026-05-03

Scope: current Raidar implementation, benchmark objectives, scenario contracts, generated benchmark artifacts, and the benchmark web app reviewed with Playwright at `http://localhost:4174`.

Constraint: `docs/` was not inspected because project instructions prohibit reading or searching it without explicit consent.

## Current Implementation Summary

Raidar benchmarks `AgentSpec`s, defined as `harness + model`, against versioned scenario contracts. The current implementation has these major surfaces:

- Scenario contracts in `scenarios/**/scenario.yaml`, with prompts, rules, starters, verification gates, requirement checks, metrics, and optional visual baselines.
- Benchmark artifacts in `experiments/benchmarks/**`, including `experiment-summary.json`, `experiment.json`, `report.md`, and per-run evidence under `runs/*`.
- Static benchmark dashboard generated by `benchmark-view/scripts/build-data.mjs` into `benchmark-view/src/data.json` and rendered by `benchmark-view/src/index.html`.
- Existing dashboard sections: decision summary, AgentSpec leaderboard, score/runtime scatter, revision trajectory, revision deltas, failure clusters, scenario revision diff, metric breakdown, evidence paths, and benchmark runs.

Existing scenario coverage is useful but narrow:

- `hello-world-smoke`: integration smoke validation.
- `homepage-implementation`: greenfield UI implementation with visual regression.
- `skill-benchmark-coding-test`: greenfield utility implementation with tests and gates.

## UX Findings

### Finding 1: The dashboard is strong for high-level selection but weak for diagnosis

The current dashboard helps answer “which AgentSpec looks best?” but not reliably “why did this AgentSpec improve or fail?”

Evidence:

- The leaderboard ranks by decision, score, validity, gates, duration, tokens, and sample.
- Failure clusters only show counts and up to two model names.
- The app does not expose failing gate names, requirement check IDs, requirement gaps, or run-level root causes in the UI.

Impact:

- Users cannot confidently decide which prompt, scenario, harness, or model change caused a score movement.

### Finding 2: Metric breakdown over-promises metric-level analysis

The UI presents `Metric breakdown` as composite evidence by metric outcome. In the reviewed utility scenario, it only showed `artifact-checks`.

Evidence:

- `skill-benchmark-coding-test v003` had an evaluation profile containing functional, requirements, verification-stability, execution-validity, resource-efficiency, test-coverage, requirements-coverage, and artifact-checks.
- The UI only displayed `artifact-checks 3 0 100%`.

Impact:

- Users cannot inspect which specific metric families drove score changes.

### Finding 3: Revision movement lacks enough comparability context

The dashboard shows revision trajectory and deltas, but the deltas are primarily composite score, duration, and tokens.

Evidence:

- `skill-benchmark-coding-test v001→v003` showed `+0.006`, `duration -11.9s`, and `tokens -7.3K`.
- The scenario diff showed prompt and scenario contract changes.
- The UI did not connect the prompt/checklist changes to gate pass-rate improvement from `33%` to `100%`.

Impact:

- Users may attribute score movement to AgentSpec quality when scenario contract changes or prompt specificity are the real cause.

### Finding 4: Failure clusters are too coarse

The current clusters are invalid, gate unstable, unscored, sparse sample, slow, and token heavy.

Evidence:

- For `skill-benchmark-coding-test`, `Gate unstable` showed `1` and named `gpt-5.4-mini`, but not which gate failed or which run failed.

Impact:

- Users cannot quickly identify whether to improve lint guidance, tests, type safety, build behavior, or requirements wording.

### Finding 5: Evidence paths are not enough as a UX affordance

The app displays artifact paths as text.

Evidence:

- Evidence paths showed `experiment-summary.json`, `experiment.json`, and `report.md` paths.
- There was no in-app run drawer summarizing verifier artifacts.

Impact:

- The dashboard requires manual filesystem inspection to understand failures.

### Finding 6: Latest and historical benchmark artifacts are mixed

The leaderboard can show repeated AgentSpec rows from separate experiments.

Evidence:

- The dashboard listed multiple rows for similar or identical `hello-world-smoke` AgentSpecs.
- The app does not clearly default to latest benchmark per `scenario + revision + AgentSpec`.

Impact:

- Ranking can be confusing because historical repeats compete with current baselines.

### Finding 7: Sample adequacy is visible but not forceful enough

Sample adequacy appears in the leaderboard and decision summary, but low adequacy still appears as normal leaderboard evidence.

Evidence:

- `skill-benchmark-coding-test` rows had `60%` sample adequacy and still ranked at the top.
- Several smoke rows had `20%` sample adequacy.

Impact:

- Users may over-trust provisional benchmark results.

## Gaps And Contradictions

- `C1`: The app says `Metric breakdown`, but current dashboard data may only expose `artifact-checks`, so the UI over-promises metric-level diagnosis.
- `C2`: The dashboard supports revision comparison, but does not yet sufficiently protect users from interpreting non-comparable scenario revisions as pure AgentSpec improvement.
- `C3`: Current scenario coverage is too narrow for broad common SWE task analysis: smoke, homepage UI, and utility coding do not cover bug fix, refactor, API, dependency, performance, or instruction-following scenarios.

## Beneficial Suggestions

- `S1`: Prioritize per-run verifier artifact ingestion before UI polish. That unlocks root-cause analysis.
- `S2`: Add 3-5 new scenario families before tuning the decision score formula, otherwise optimization will overfit to utility, UI, and smoke behavior.
- `S3`: Treat low sample adequacy as provisional in the UI. It should be visually distinct from robust benchmark evidence.

# User Journey And Flow Review

## Core Problem

The current benchmark web app exposes many useful data views, but it presents them as one dense analytical surface. That makes it hard for a user to understand what task they are performing, what decision they are expected to make next, and where to go after finding a signal.

The dashboard currently behaves like a comprehensive artifact browser. The target experience should behave more like a guided benchmarking workbench:

- Start with the user objective.
- Select the relevant scenario family or AgentSpec decision.
- Surface only the evidence needed for that task.
- Progressively reveal diagnostic detail.
- End with a clear next action: select an AgentSpec, improve a scenario revision, rerun a benchmark, or inspect a failure.

## Primary User Journeys

The ten scenario candidates imply six major user journeys. These should drive the app structure more than the current artifact-centric layout.

### Journey 1: Choose The Best AgentSpec For A Task

Applies to:

- Greenfield utility implementation.
- Bug fix with regression test.
- Frontend component implementation.
- Full page UI implementation.
- API/data flow change.

User question:

- Which AgentSpec should I use for this type of SWE task?

Current issue:

- The leaderboard starts globally and mixes scenario types, revisions, historical artifacts, and sample sizes.
- The user has to infer whether they are comparing suitable evidence.

Recommended flow:

1. Pick task type.
2. Pick scenario family.
3. See recommended AgentSpec shortlist.
4. Compare shortlisted AgentSpecs on the relevant signals for that task.
5. Open evidence only if a recommendation is disputed or marginal.

What should be shown:

- Task selector: `Bug fix`, `Utility`, `UI page`, `Component`, `API`, `Refactor`, `Coverage`, `Dependency`, `Performance`, `Instruction following`.
- Scenario family card with purpose, revisions, and signal coverage.
- Top 3 AgentSpecs for that task.
- Confidence label based on sample adequacy and revision comparability.
- Task-relevant signal chips, not every metric.

Logical target:

- `Use this AgentSpec` recommendation or `Need stronger evidence: run more repeats / add scenario coverage`.

### Journey 2: Improve A Scenario Revision

Applies to:

- All ten scenarios.

User question:

- How should I revise this scenario so it better measures the target SWE capability?

Current issue:

- Scenario diffs, revision deltas, and failure clusters are separated.
- The app does not explain what change likely caused the observed movement.

Recommended flow:

1. Select scenario family.
2. Select revision pair.
3. Review comparability warning.
4. Inspect score movement and root-cause movement together.
5. Get suggested next revision amendments.

What should be shown:

- Revision pair selector: `v001→v002`, `v002→v003`, `first→latest`.
- Contract change summary: prompt, gates, requirements, metrics, visual baseline, starter.
- Movement summary: score, gate pass, validity, duration, tokens, requirements coverage, requirements adherence, visual.
- Root-cause deltas: failures removed, failures introduced, new evidence gaps.
- Suggested next amendments.

Logical target:

- `Clone next revision` or `Run benchmark against revised scenario`.

### Journey 3: Diagnose Why An AgentSpec Failed

Applies to:

- Bug fix.
- Refactor.
- Dependency/tooling upgrade.
- API/data flow.
- Repository instruction following.

User question:

- Why did this AgentSpec fail or underperform?

Current issue:

- Failure clusters are too abstract.
- Evidence paths require filesystem inspection.

Recommended flow:

1. Start from failing AgentSpec row or failure cluster.
2. Open run-level diagnostic drawer.
3. See gate failures, requirement check failures, requirement evidence gaps, and artifact changes.
4. Compare failed run against successful run.
5. Decide whether the issue is AgentSpec weakness, scenario ambiguity, environment instability, or insufficient sample.

What should be shown:

- Failure reason headline: `lint failed`, `tests missing`, `visual mismatch`, `requirement unmapped`, `invalid run`, `timeout`.
- Failing run IDs.
- Failed command and gate name.
- Relevant verifier output summary.
- Missing requirement check IDs.
- Workspace diff summary.
- Similar successful run for comparison.

Logical target:

- `Improve prompt guidance`, `Improve scenario checks`, `Exclude invalid run only through rerun workflow`, or `Pick different AgentSpec`.

### Journey 4: Validate That A Revision Improved Reliability

Applies to:

- Greenfield utility implementation.
- Full page UI implementation.
- Test coverage expansion.
- Performance optimization.

User question:

- Did the scenario revision actually improve reliability, or did it just change the benchmark?

Current issue:

- The current trajectory view is score-first and does not emphasize gate stability, sample confidence, or comparability.

Recommended flow:

1. Select scenario family.
2. Select AgentSpec chain across revisions.
3. View reliability trend before quality trend.
4. Confirm sample adequacy and comparable contract.
5. Inspect root causes for residual failures.

What should be shown:

- Reliability-first summary: valid rate, gate pass rate, unscored count, repeat failures.
- Then quality: composite, requirements coverage, requirements adherence, visual, coverage.
- Then efficiency: duration, tokens.
- Comparability banner.
- Confidence badge.

Logical target:

- `Trust revision movement`, `Run more repeats`, or `Revision is not comparable enough`.

### Journey 5: Understand Scenario Portfolio Coverage

Applies to:

- All ten scenarios, especially missing scenario families.

User question:

- Do our benchmarks cover the common SWE work we care about?

Current issue:

- The app starts with artifacts, not the scenario portfolio.
- Missing scenario types are invisible.

Recommended flow:

1. Open portfolio page.
2. Review scenario families by SWE task type.
3. See covered, partially covered, and missing task types.
4. Inspect signal coverage by family.
5. Decide which scenario to create or improve next.

What should be shown:

- Matrix of task types vs scenario families.
- Revision count per family.
- Evidence quality per family.
- Missing signal warnings.
- Suggested next scenario families.

Logical target:

- `Create new scenario`, `Clone revision`, or `Run matrix for under-sampled scenario`.

### Journey 6: Compare Cost, Speed, And Quality Tradeoffs

Applies to:

- Performance optimization.
- AgentSpec selection.
- Dependency/tooling upgrade.
- Greenfield implementation tasks.

User question:

- What is the best value AgentSpec for this task type?

Current issue:

- Cost/value exists as a decision card, but tradeoff exploration is shallow.
- The scatter plot is useful but not connected to task-level recommendations.

Recommended flow:

1. Select task type and scenario family.
2. Choose tradeoff mode: `highest quality`, `most reliable`, `fastest acceptable`, `best value`.
3. See recommendation changes by mode.
4. Inspect frontier chart.
5. Confirm weak points and sample confidence.

What should be shown:

- Tradeoff mode tabs.
- Pareto frontier: quality vs duration, quality vs tokens.
- AgentSpecs dominated by better alternatives should be visually de-emphasized.
- Confidence and sample warnings.

Logical target:

- `Use cheapest acceptable`, `Use highest quality`, or `Run more samples before deciding`.

## Recommended Information Architecture

The current single-page dashboard should be split into focused pages. More pages are justified because each page would carry less cognitive load and have a clearer purpose.

### Page 1: Overview

Purpose:

- Orient the user and route them into the right workflow.

Content:

- Top-level benchmark health.
- Scenario portfolio coverage summary.
- Latest recommended AgentSpecs by task type.
- Alerts: sparse samples, non-comparable revisions, failing gates, missing signals.
- Primary calls to action.

Primary navigation targets:

- `Choose AgentSpec`.
- `Improve Scenario`.
- `Diagnose Failures`.
- `Scenario Portfolio`.

What to remove from this page:

- Full leaderboard.
- Full run table.
- Full diffs.
- Full metric breakdown.

### Page 2: Choose AgentSpec

Purpose:

- Help the user select the best AgentSpec for a scenario/task.

Content:

- Task type selector.
- Scenario family selector.
- Tradeoff mode tabs: `Best overall`, `Most reliable`, `Fastest acceptable`, `Best value`.
- Shortlisted recommendations.
- Comparison table with only task-relevant columns.
- Confidence warnings.

Progressive detail:

- Recommendation cards first.
- Table second.
- Evidence drawer on demand.

### Page 3: Scenario Revisions

Purpose:

- Understand whether scenario revisions improved the benchmark and how to revise next.

Content:

- Scenario family header.
- Revision timeline.
- Revision pair selector.
- Comparability banner.
- Attribution panel: contract changes next to metric movement.
- Suggested next amendments.
- Prompt/scenario diff as expandable detail.

Progressive detail:

- First show summary and confidence.
- Then show movement details.
- Then show raw diff.

### Page 4: Failure Diagnosis

Purpose:

- Turn failures into actionable fixes.

Content:

- Failure root-cause clusters.
- Filters by scenario, AgentSpec, gate, failure category.
- Run-level diagnostic drawer.
- Failed vs successful run comparison.
- Suggested action based on failure pattern.

Progressive detail:

- Root-cause cards first.
- Affected AgentSpecs second.
- Run evidence third.

### Page 5: Scenario Portfolio

Purpose:

- Show benchmark coverage across common SWE tasks.

Content:

- Task-type matrix.
- Existing scenarios mapped to task types.
- Missing scenario types.

## Attention And Visual Hierarchy

The current theme uses a narrow black, gray, white, and orange palette. It is coherent, but everything has similar urgency. The interface needs more semantic variation so users can separate decisions, warnings, evidence, and neutral metadata.

### Recommended Semantic Palette

Keep the existing dark editorial base, but add semantic roles:

- Decision accent: orange, reserved for selected recommendation or primary CTA.
- Success: green or teal, for reliable/pass/improved.
- Warning: amber, for sparse sample, partial comparability, high cost.
- Critical: red or coral, for invalid, failing gates, non-comparable revisions.
- Evidence: blue or steel, for links, artifacts, drilldown affordances.
- Neutral: gray, for metadata and inactive states.

The exact colors should be muted enough to fit the current visual language. The important change is semantic separation, not brighter decoration.

### Recommended Urgency Levels

Use a consistent severity model:

- `Critical`: invalid results, non-comparable revision, zero scored runs, required gates failing.
- `Warning`: sparse sample, high variance, partial comparability, high token/duration outlier.
- `Positive`: high confidence, gate-stable, sample adequate, improved revision.
- `Neutral`: metadata, filters, raw paths, unchanged metrics.

### Layout Density Changes

Reduce default density by moving details into drawers and subpages:

- Overview should show fewer than 8 cards.
- Recommendation tables should default to top 5 rows.
- Raw benchmark runs should move to Evidence Explorer.
- Diffs should be collapsed behind `View diff` unless the user is on Scenario Revisions.
- Metric breakdown should be hidden unless data is complete enough or explicitly requested.

### Visual Emphasis Rules

- One primary orange CTA per page.
- Critical warnings should be visually stronger than recommendation accents.
- Evidence links should use a separate color from warnings.
- Score deltas should use direction color only when the movement is comparable and sample-supported.
- Low-confidence deltas should be muted or hatched, not shown as strong green/red movement.

## Recommended End-State Flow

The ideal web app flow should be:

1. User lands on Overview.
2. Overview highlights benchmark health and asks what they want to do.
3. User selects a task-oriented workflow.
4. The workflow filters the data to relevant scenarios and signals.
5. The UI shows recommendation or diagnosis first.
6. Raw evidence remains one click away, not always visible.
7. Every analytical view ends with a next action.

Concrete example for `skill-benchmark-coding-test`:

1. User opens `Scenario Revisions`.
2. Selects `Greenfield utility` and `skill-benchmark-coding-test`.
3. Sees `v001→v003`: score `+0.006`, gates `33%→100%`, tokens `-7.3K`, duration `-11.9s`.
4. Sees attribution: prompt added explicit verification checklist and lint/import-order guidance.
5. Sees confidence warning: sample adequacy `60%`, preferred sample not met.
6. Next action: `Run 2 more repeats` or `Clone v004 to test another guidance change`.

Concrete example for `homepage-implementation`:

1. User opens `Choose AgentSpec`.
2. Selects `Full page UI`.
3. Chooses tradeoff mode `Best visual quality` or `Fastest acceptable`.
4. Sees top AgentSpecs with visual region scores, gate pass, sample adequacy, and token cost.
5. Opens a visual failure drawer for weak regions.
6. Next action: `Pick AgentSpec`, `Inspect visual evidence`, or `Improve prompt for failing region`.

## Additional Gaps And Contradictions

- `C4`: The current app is organized around available artifacts, but the likely user workflows are task-oriented: choose an AgentSpec, improve a scenario, diagnose failure, validate revision reliability, or inspect portfolio coverage.
- `C5`: The single-page layout makes all analysis modes compete for attention even though most users need only one workflow at a time.
- `C6`: The visual system has too few semantic states, so recommendation, warning, evidence, and metadata compete at similar urgency.

## Additional Beneficial Suggestions

- `S4`: Design the app around six user journeys before adding more charts. Otherwise the dashboard will become more powerful but less navigable.
- `S5`: Introduce task type as a first-class concept in the data model and URL state so links can open directly to `Choose AgentSpec / Full page UI` or `Failure Diagnosis / Bug fix`.
- `S6`: Treat the Evidence Explorer as an expert mode. Most users should encounter raw artifacts only after a recommendation, warning, or failure root cause points them there.
