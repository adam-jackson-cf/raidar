## Workflows

- Public interface: repo-root `make ...`
- Use `make help` for command discovery and target descriptions.
- Treat direct `uv run --project orchestrator raidar ...` as implementation detail behind the root `Makefile`.
- LiteLLM must stay exact-pinned to a known-safe release across manifests and lockfiles. Do not use `1.82.7` or `1.82.8`.
- Keep `README.md` as the only human entrypoint; do not duplicate exhaustive command lists in other docs.
- Vocabulary (schema v2, requirements change log 2026-10-02): use Harbor's terms wherever Harbor has one. A **job** is one execution of a locked experiment (`var/jobs/`, `job.json`, `job.lock.json`, `JOB=`/`JOB_ID=`/`JOBS_DIR=`); a **trial** is one arm × attempt × problem (was "trajectory"); a **step result** is one checkpoint of a trial; **attempts** are the paired, counterbalanced replicates (was "blocks"; `analysis.attempts`); the **verifier** is the hidden grader (was "oracle"; `raidar.grading`) and its per-step output is the **reward**; an agent is named by Harbor's `AgentName` (`codex`, `claude-code`; was harness `codex-cli`); `environment.type` replaces `runtime.environment`; the headline **metric** (`assessment.metric`) replaces the headline policy. Keep *problem* and *checkpoint* (SCB) and Raidar's *experiment*, *arm*, *condition*, *component*, *factor*, *lock*, *verdict*. Harbor's `oracle` agent (`AGENT_OVERRIDE=oracle`) keeps its name.
- Identity-bearing artifacts keep their bytes and pre-v2 words unless a release is intended: the fingerprint sources of components (listed in each built-in's manifest as repo-relative paths, such as `orchestrator/src/raidar/contract/snapshot.py`, and for `python-guardrails` its payload under `lab/treatments/python_guardrails/`; so `raidar/contract/snapshot.py`, `raidar/subject/agent/harness.py` and the `Harness` CLI ids stay), the grader plugin `raidar/grading/runtime/raidar_oracle_plugin.py`, the Python pack image recipe (`lab/environments/python/`: `pack.yaml`, `image/`) and the verifier evidence names inside Harbor trial directories (`raidar-oracle/`, `oracle_leak`, `oracle_bundle`, `oracle-bundle.json`). Scorers' identities work the same way: the observation subject value `trajectory` (`TRAJECTORY_SUBJECT`, `ObservationSubject.TRAJECTORY`), the evidence input `oracle.cases` and scorer manifest descriptions are hashed into every Assessment key, and the problem store's bundle directory `oracle/` is inside each problem's pinned digest (`scb/forge@38d627ecf668`). Changing any of them is a release: run `make release-archive REF=<name>@<N>` for each affected component or scorer, edit in place, bump its `@N` (or the pack contract) and relock.
- The experiment is the only authoring unit: one `experiment.yaml` at `lab/experiments/<kind>/<id>/experiment.yaml` (with its lock and `components/`), `schema_version: 2`, naming its `kind` (`ab-test`, `benchmark`, `smoke`; `research-loop` is reserved), one `runtime` (a pack id), pinned `problems`, `agents`, `conditions` (lists of components; optional `shared_components` are put ahead of every condition's own, identically), `arms` (one condition on one agent), `assessment` (`scorers`, optional `metric`) and `analysis` (`baseline_arm`, `attempts`, `seed`, verdict thresholds, `rank_by` for benchmarks, optional `primary_outcome`: the pre-registered primary the report, markdown and review surface label, default the progression's `solve_rate`/`reached`; an errata-applied primary is always reported with its raw counterpart beside it). The id is `<runtime>__<subject>__<intent>` (`NAME2`) and the directories are its kind and id (`NAME1`). Do not reintroduce scenario, revision or matrix files.
- Kinds: an `ab-test` compares conditions (`factors` include `condition`; `agent.*` may be added). A `benchmark` is one experiment comparing agents under one condition (factors are `agent.*` only); its baseline arm is the reference agent and its analysis adds a ranking view (mean ± CI, pass@k, cost, tokens). A `smoke` runs the normal engine and its reports are stamped not citable. To compare models, write one benchmark, not a group of experiments.
- Lifecycle: `make experiment-validate` -> `make experiment-lock` -> `make experiment-plan` -> `make experiment-execute` (each with `EXPERIMENT=lab/experiments/<kind>/<id>/experiment.yaml`; execute also `JOB_ID=`) -> `make experiment-assess JOB=var/jobs/<id>/<job> STORE=var/stores/<id> SCORERS="..."` -> `make experiment-analyze JOBS="var/jobs/<id>/<job>" STORE=var/stores/<id> ANALYSIS_OUT=var/analysis/<id>` -> `make review-surface-quality-data QUALITY_JOBS=var/jobs/<id> QUALITY_STORE=var/stores/<id>` -> `make review-surface-serve REVIEW_JOBS_ROOT=var/jobs/<id> REVIEW_STORE=var/stores/<id>`. Rescoring and analysis use the assessment settings of the job's lock (the experiment's current lock when its `lock_sha256` matches, else the job's own `job.lock.json`); pass `LOCK=`/`REVIEW_LOCK=`/`QUALITY_LOCK=` only for a lock kept elsewhere (smoke locks live under `var/tmp/smoke/`). Old make variable names (`RUN=`, `RUNS=`, `HARNESS=`, `BLOCK=`, ...) fail with their new name.
- Use `make experiment-init EXPERIMENT=lab/experiments/ab-test/<id>/experiment.yaml [PROBLEM=<ref>]` only to start a brand-new experiment; it writes a two-arm ab-test starter and refuses an existing path.
- To test another variant of a treatment, add a condition and an arm inside the existing `experiment.yaml` so it stays paired with the baseline arm. Create a new experiment only for a new question (different problems, baseline arm or analysis plan); do not create a sibling experiment for a variant. Arms may differ only in the declared `factors`.
- Use `make experiment-plan EXPERIMENT=<path>` to inspect an experiment's resolved contract (every trial with its hashes), `make problem-list` to see the registered problems, and `make problem-info PROBLEM=<ref>` to inspect one.
- Long jobs (any real-LLM `make experiment-execute`, and anything expected to outlive the current shell or agent turn) must be launched detached with `DETACH=1` (`make experiment-execute EXPERIMENT=... JOB_ID=... DETACH=1`): a supervisor in its own session runs the job, keeps it awake (`caffeinate -i` on macOS) and writes its pid, log and exit record to `<job dir>/detach/`. Then monitor it to completion with `make experiment-status JOB=var/jobs/<id>/<job>` (`state: running|finished|failed|died`). Never start a long job as a session-bound background task (`&`, a tool's background mode): it dies with the session, as `main-01` of the guardrails experiment did. A finished detached job is assessed and analysed as usual.
- Any change to an experiment, a component file or a problem pin requires `make experiment-lock` before the next job (`make experiment-execute` refuses a stale lock). Never hand-edit a `*.lock.json`. Each job needs a new `JOB_ID`; a job directory is never reused.
- Runtime-compatibility gate: `make experiment-lock` (and so plan, execute and the smoke targets, whatever `EXPERIMENT_SET` overrides) refuses with field-level `RT0`-`RT6` errors, all at once: unvalidated binding (RT0), binding runtime ≠ experiment runtime or a local `path:` task without `[metadata] raidar_runtime` (RT1), binding imported against another pack contract (RT2), component not covering the runtime or the arm's agent (RT3), scorer or headline metric not covering the runtime (RT4), agent version ≠ pack pin (RT5), no pack for the runtime or pack drift at plan/run (RT6). `make experiment-assess`/`assess-regrade` check scorers and `--bundle` against the job's lock (AS1). Never work around a refusal; fix the design or re-import the binding.
- Lock provenance: a lock's `toolchain` section hashes the Raidar spec code and every locked scorer's implementation (including its imports). Any semantic change under `orchestrator/src/raidar/design/experiment/`, to `contract/canonical.py`, `contract/references.py`, `contract/source_digest.py` or `scoring/framework/metrics.py` (`SPEC_EXTERNAL_MODULES`), or to a scorer module therefore makes every `lab/experiments/*/*/*.lock.json` stale, and `make experiment-locks-check` (part of `make quality`) fails until each is relocked with `make experiment-lock EXPERIMENT=<path>`. Relock the experiments in the same change.
- A scorer, headline-metric, threshold or toolchain relock keeps `lock_sha256` (it covers the execution section only), so existing jobs still match: rescore them into the Assessment store with `make experiment-assess` instead of rerunning agents. A changed `lock_sha256` means a new experiment.
- Problems come only from the pinned registry: `make problem-import PROBLEM=<ref>`, then `make problem-validate PROBLEM=<ref>` when `lab/problems/registry/` has no validation report for it. A source key in `lab/problems/sources.yaml` binds one runtime (`runtime:`, default `python`; another runtime's binding would be `scb-<runtime>`). The verifier bundle and held-out tests stay on the host; never place them in an agent workspace or a component.
- Toolchains come from runtime packs (code in `orchestrator/src/raidar/subject/environment/<runtime>/`, loaded by `raidar.subject.environment.load_runtime_pack`; the recipe `pack.yaml`, `tools.lock.yaml` and `image/` is data in `lab/environments/<runtime>/`): `make pack-info`, `make pack-build`, `make pack-audit`. Agent images carry no scorer tools, and an agent's `version` must equal the pack pin. Do not start packs for other runtimes until the Phase 1 process is signed off.
- Scoring is offline: `make experiment-assess` writes Assessments to a store outside the job and never re-runs agents. A scorer, component or headline metric has one module, edited in place; a behaviour change bumps its manifest `@<N>`, and the release being replaced is preserved first with `make release-archive REF=<name>@<N>` (annotated tag `archive/<name>@<N>`; it refuses an existing tag). Recover an old release's code from its tag, never from a second module in the tree.
- `protocol.verifier_coverage: offline` takes the verifier's per-test coverage pass (G's evidence) off the trial's critical path: trials grade without it, and `make experiment-assess` with `code-quality@3` first makes each step's coverage run from its stored snapshot into the store (never the job). `make assess-regrade JOB=<trial-or-job> COVERAGE_CHECK=1 [STORE=]` makes the runs again and compares them with the trial's own pass or the stored run. Left unset (`trial`), nothing changes and the field stays out of locks.
- Real-LLM trials default to agent `codex` with `gpt-6-luna` at `low` reasoning effort. Containers run on the machine's Docker **target** (ADR-002): `~/.config/raidar/targets.toml` names targets (`make target-init`, `make target-list`, `make target-status TARGET=<name>`); `TARGET=<name>` selects one, else `$RAIDAR_TARGET`, else the file's `default`; with none of these a command fails (the current Docker context is never used). A remote target's SSH-forwarded socket is supervised by `make target-up`/`target-down`, and jobs reconnect and reap a lost trial's containers on their own. Hidden tests and agent credentials go only to targets with `trusted = true`. `job.json` records the resolved `execution_target` and `mechanics_epoch`; never pool timing or cost across targets. After a stopped job use `make harbor-cleanup JOB=<job-dir>`; `make target-prune` removes stale trial projects on a target. On a shared Docker host never touch containers Raidar did not create.
- Exclude component payloads under `lab/experiments/**/components/**` (rules files, skills, starter files) from analysis and code-quality checks by default; they are treatment content delivered to agents, not canonical shared product code.
- Treat everything under `var/` (`var/jobs/`, Assessment stores in `var/stores/`, analysis output in `var/analysis/`, `var/problems/store/`, `var/problems/cache/`, `var/tmp/`, `var/archive/`) as generated runtime artifacts by default: exclude them from quality checks unless the request explicitly asks to review/analyze them. `lab/` is tracked (definitions only).

- Layout: `orchestrator/` (the `raidar` package, tests), `review-surface/` (UI), `lab/` (tracked experiment definitions: `lab/experiments/<kind>/<id>/`, `lab/problems/` pins, manifests and fixtures, `lab/ledger/` fault and remedy records, and the data the code loads at run time: `lab/treatments/<component>/` component payloads, `lab/environments/<runtime>/` pack recipes, `lab/judge/` judge policies and question sets, each reached through one explicit path in `raidar/contract/paths.py`), `docs/`, `scripts/`, `.agents/` and `.claude/` (skills, agent config), `.github/`, and the git-ignored generated root `var/`. `make structure-check` (part of `make quality`) refuses any other top-level directory, any second-level `lab/` entry outside `experiments, problems, ledger, treatment, environment, judge`, any `raidar` top-level package outside `cli, evaluation, engine, design, scoring, grading, subject, contract`, any second-level subpackage outside its group's list (below), packages nested deeper than three levels below `orchestrator/src/raidar` (no exemptions: run-time data lives under `lab/`) and any path carrying a version.

Never keep two implementations side by side; `make release-archive REF=<name>@<N>` tags the release before an in-place edit. The one exception is hand-edited, immutable payload data in `v<N>/` folders under a `components/` directory or under `lab/treatments/`.

## Objectives

Every use of Raidar's tools serves one of two objectives. Name the objective before designing or running a job, and work to its rules. If the user has not said which one applies, assume **explore**.

- **Explore**: improving Raidar's process, or an early idea for an experiment revision (a new condition, component, scorer or gate). The goal is to validate that something works and look for early signals with the fewest runs.
  - Check first with the smallest run that can fail: a no-LLM fixture, `make orchestrator-smoke`, or 1-2 trials of the arm under test. Then run at most 4 attempts per arm, on one problem and the default agent (`codex`, `gpt-6-luna`, low).
  - Report signals, not conclusions. Report effect direction, process and component behaviour (probes, gate rounds, manipulation checks), fault categories, cost, and anything broken. Verdicts below `min_pairs` read `insufficient` by design. Call findings exploratory; never cite them as evidence of an effect.
  - Stop when a process defect appears. Fix it, then rerun small. Do not add attempts while the process or the treatment is still changing.
  - Still lock and pre-register, because both are cheap. A power target is not required.
- **Confirm**: the system and the treatment are settled, and the goal is conclusive evidence or a comparison across agents.
  - Enter only when nothing Raidar-side touching the experiment is pending: verifier, scorers, components, gate and errata are stable. An explore run of the exact design must have completed cleanly.
  - Pre-register before the first job: the primary outcome (in `rationale.md` beside the experiment), the verdict thresholds (in the lock) and the attempts per arm. Size attempts from the `J2` sample-size projection of earlier explore jobs for the primary outcome.
  - Run every arm under one lock with no changes mid-series. Hold at most 1 infra exclusion per arm. A Raidar or treatment change during the series starts a new experiment; it never patches the running one.
  - Compare agents with one `benchmark` experiment (agents as the factor), and treatments with an `ab-test`. Report verdicts with CIs, cost beside every effect, and the gate-effort and quality signals. Only confirm results are citable.
- Objectives are independent of kinds. An `ab-test` or a `benchmark` can be run to explore or to confirm. A `smoke` checks operational health and serves neither objective.

## Run mechanics (mechanics v1, ADR-002)

- **Run-health**: every trial writes `health.json` (checks `V1`-`V3` verdicts, `H1`/`H3`-`H6` records and limits, `L1`-`L2` liveness, `P2`-`P3` contention and warnings, `T1` tool tree unchanged, `T2` records manifest, `T3` reaper residuals; each `pass|violation|unmeasured`). V/H/T violations invalidate the trial (`health_verdicts`, `health_budgets`, `health_tamper`); `unmeasured` never does, and is not a pass. `make health JOB=<job-dir>` recomputes it (and verifies `T2`, which is `unmeasured` in-run); violations and liveness findings append provisional lines to `<job>/fault-candidates.jsonl`.
- **Liveness**: a host-side monitor samples each agent phase (output, agent-uid CPU, container network) into `<trial>/raidar-liveness.json`. `RAIDAR_LIVENESS=enforce` is the default: after the idle window (`RAIDAR_LIVENESS_IDLE_S=600`, sampled every `RAIDAR_LIVENESS_INTERVAL_S=15`) it kills the agent uid, and the step is verified and graded on what exists, exactly like an agent timeout (the trial stays valid; L2 is a pass with the finding `idle_killed`, with the idle seconds and killed pids, and a provisional line in `fault-candidates.jsonl`). `observe` (record `idle_observed`, never kill) and `off` are opt-outs. Calibration is ADR-002 A.9. Harness and treatment time limits always win; Raidar never retries a trial.
- **Smoke-before-measure**: `make experiment-execute` refuses non-smoke kinds unless a clean smoke job matches the toolchain hash, pack recipe, every arm's agent/model/effort and the execution target. Clean means all trials valid, no health violations, and in every trial every executed step's agent changed `/app` (the step's recorded snapshot digest differs from its parent's; the first step's parent is the empty tree), so a smoke where the agent only asked a question never clears a run; the refusal names the job, trial and step. `ALLOW_UNSMOKED=1` overrides and is recorded in `job.json` `admission`; never use it for a citable (`confirm`) job.
- **Provenance and pooling**: `job.json` records `runner` (commit, dirty, toolchain hash), `recipes` (pack, graders), `effective_limits`, `execution_target`, `mechanics_epoch` and per-trial records-manifest digests. `make experiment-analyze` with 2+ jobs refuses to pool across differing epoch, toolchain, dirty runner, pack/grader recipe, subject, effective limits, or (for timing and cost) target hardware. `POOL_OVERRIDE=<field>[,<field>]` lifts named refusals and is recorded in the analysis; a records-manifest (tamper) violation never lifts. Jobs before the mechanics epoch are labelled `unmeasured`.
- **Fault ledger**: tracked fault categories (`lab/ledger/faults/FCR-NNN.md`) and remedies (`lab/ledger/remedies/M-NNN.md`) with YAML frontmatter and a `status_history`. Edit records through the `fault-catalog` skill, then run `make ledger-index && make ledger-check` (`ledger-check` is part of `make quality`; `lab/ledger/README.md` is generated). Occurrence candidates stay in the job directory, not the ledger.
