# ADR-001: Harbor-kernel reboot

- **Status:** Accepted (approved by the user, 2026-09-29)
- **Date:** 2026-09-29
- **Authority:** `docs/reboot/requirements.md` (v1, frozen 2026-09-29). Requirement IDs (F*, N*) are cited inline.
- **Background:** `docs/reboot/design-memo.md` (§10 superseded options, §11 candidate architecture, §12 review surface and quality port). `docs/reboot/implementation-plan.md` (Phase 0 and Phase 1).
- **Evidence shorthand:** **S** = SCB fork (`slop-code-bench`), **P** = `scb-problems` (SCB problems + Harbor converter). `[INFERENCE]` marks claims not directly observed.

## 1. Context

Raidar benchmarks coding agents (harness + model) against problems with hidden oracles, then changes starting conditions and measures paired effects. The scenario-era design bundled problem, conditions, scorers and weights into one versioned "scenario". That coupling blocked clean arm comparisons and made scorers decide success (design-memo §1).

Forces on this decision:

- **Checkpointed problems (F1, F3).** A problem has 1..N checkpoints. Each checkpoint is a fresh agent that meets only what is in the workspace: no prior conversation, harness state reset to the Condition baseline, and no surviving agent processes. The environment and workspace persist.
- **Hidden, trusted oracle (F4, N2).** Oracle tests never enter the agent's environment, and the agent never sees oracle results. Progression is `continue` (default) or `halt_on_failure`.
- **Minimal bespoke code (N4).** Harbor is the execution kernel. Raidar owns experiment design, components, the oracle plugin, scorers, Jev, analysis and the review surface.
- **Reproducibility (N3).** Harbor, harness, model and tool versions are pinned or recorded.
- **Current state.** The installed Harbor is `0.1.42`. It has no `[[steps]]` task model, and Raidar does not pin it. PyPI's latest is `0.23.0` (design-memo §10.2).
- **Problem source (F13).** SCB publishes SlopCodeBench as a Harbor multi-step dataset (design-memo §11).

## 2. Decision

### 2.1 Requirements freeze

Requirements v1 is frozen as of **2026-09-29** (`docs/reboot/requirements.md`). It is the yardstick for every task in the implementation plan. Any change needs an explicit user decision, recorded in that file's change log. The v1 freeze records these decisions: F2 (start at checkpoint k) removed; N1 reframed as framework-overhead budgets; F12 review surface frozen; F14 port of the SCB-fork quality scoring; F15 one-shot policy; the headline-policy mismatch warning.

### 2.2 Checkpoint mechanism: option A′

Each trajectory runs as **one Harbor multi-step trial** (`[[steps]]`, one step per checkpoint):

| Aspect | Rule |
|---|---|
| Environment | **One container** for all steps. `/app` and the environment persist across checkpoints (F3) |
| Agent | A **fresh headless agent process per step**. No conversation carries over |
| Harness state | Reset per step. Claude Code: Harbor sets `CLAUDE_CONFIG_DIR=/logs/agent/sessions` and wipes it per step. Codex: `CODEX_HOME` persists across steps, so the per-step `setup.sh` clears it |
| Process reaping | A generated **per-step `setup.sh`** kills leftover agent-user processes and resets harness state to the Condition baseline. Harbor does not reap between steps itself (open PR #3454) |
| Artifacts | Per-step `/app` snapshot, ATIF trajectory, timing and usage land on the host |
| One-shot | A one-shot problem (N=1) is a 1-step task through the same path (F1) |

### 2.3 Oracle placement: host-side verifier

The oracle is a **custom Harbor `BaseVerifier`**, loaded via `verifier.import_path`, running in the Harbor host process:

1. It downloads the step's `/app` snapshot.
2. It runs the hidden tests against a **copy** in a fresh, no-network sandbox (container or subprocess).
3. It normalises results to `CaseResult{id, group, checkpoint_origin, status}`, graded strict all-cases.

Consequences for F4 and N2:

- **Tests are never uploaded** to the agent's environment. No `tests/` directory exists there at any step.
- The verdict is returned to Harbor as the step reward only. The agent receives no oracle output.
- Because verification is host-side, Harbor's `min_reward` halt is safe, so `halt_on_failure` is native. Strict metrics (`reached`) remain derivable from `continue` runs, so halting is only a cost saving.
- The host-side verifier removes the dependency on the unreleased in-environment verifier fix (Harbor #1961; leak class #1960).
- Offline regrading reruns the same verifier over stored snapshots with `raidar assess --regrade`. Harbor's `harbor trial regrade` is not used: it requires separate-mode verifiers, and the Raidar oracle runs in shared mode.

### 2.4 Score policies

Scorers only observe; they never decide success, apply weights or compare arms (F6). Weights live in versioned **ScorePolicies**. Each experiment declares one **headline** policy, which drives `composite_score` and the delivery tiers (F15).

| Policy | Default for | Formula |
|---|---|---|
| `scb-canonical@1` | Multi-checkpoint problems (K ≥ 2) | `S = 100·C·(0.70 + 0.30·I)`, `I = .15V + .15E + .20H + .30R + .20G` |
| `scb-canonical-oneshot@1` | One-shot problems (K = 1) | `S = 100·C·(0.70 + 0.30·I₁)`, `I₁ = .30V + .30E + .40H`. R and G are `not_applicable` (no transition). Weights are SCB's V:E:H ratio renormalised |
| `scb-canonical@2` | Declared explicitly (pilot forge) | `scb-canonical@1` plus the zero-correctness rule below |
| `scb-canonical-oneshot@2` | Declared explicitly (pilot one-shot) | `scb-canonical-oneshot@1` plus the zero-correctness rule below |

Rules:

- **C is the SCB fork's `C_p = Σ_k C_p,k / K`** (`metrics/scoring/schema.py` `FORMULAS["correctness"]`, `live_evidence._correctness`): the mean over the K planned checkpoints of each checkpoint's case pass rate, passed / graded cases with skipped cases left out. A checkpoint the trajectory never reached (the fork's unproduced checkpoint) counts 0. A reached checkpoint with no graded case makes C ineligible (the fork's `canonical_test_denominator_zero`). *Corrected 2026-10-02 (S2-SS-1):* this section first said "C = solved checkpoints / K". That is the memo's primary outcome `C_r` (`solve_rate`), not the fork's score component. Before the correction, analysis and the review projection fed solved/K into S, while the G2 golden path (`scorers/code_quality/arithmetic.py`) already used the fork's mean. All three now use the policy's definition (`spec.policies.problem_correctness`). The policy definition, and so its digest, records the C definition.
- A missing or unavailable component makes the score **ineligible**, with typed reasons. It is never scored as zero (F6). `@1` applies this to every component, exactly as the fork does: the fork marks a generation ineligible when any produced checkpoint lacks quality evidence, whatever its correctness.
- **Zero-correctness rule (`@2` only, S2-SS-2, user decision 2026-10-01).** A measured C = 0 scores S = 0 even when a quality component is missing or ineligible, because `S = 100·0·(…) = 0` for any quality values. The trajectory stays in the headline analysis. Dropping it would bias paired comparisons towards the arm that fails more. Ineligibility applies only when C > 0 and a needed component is missing, or when C itself is unmeasured. This departs from the fork, so it is a new policy version and `@1` stays fork-exact. The defaults by K are still `@1` (F15); the pilot experiments declare `@2`.
- The review surface warns when compared experiments use different headline policies (F15).

### 2.5 Scenario-epoch archive

`scenarios/`, `matrices/` and existing `experiments/` become **read-only history** (plan task 0.6).

- No new scenario revisions are accepted.
- The `raidar-revision-cleanup.md` work stops and is marked superseded.
- The review surface keeps projecting old-epoch runs until the new projection lands (plan 1.K1), and continues to render them afterwards.
- Old-epoch and new-epoch results are never pooled.

### 2.6 Harbor pin policy

- Harbor is **exact-pinned** to one release ≥ 0.23.0 in `orchestrator/pyproject.toml` and its lockfile (plan task 0.2). The chosen version is recorded in every run's provenance (N3).
- An upgrade happens **only via a spike that reruns all four 0.3 checks** (host-side verifier with no test upload, context isolation, per-step artifacts, both progression modes) on the candidate version. The spike's evidence is appended to this ADR or a successor.
- Repo-local CLI agents are ported to the pinned API as part of the pin (validated agent kwargs, `--agent` import path, hyphenated hook events, changed auth).

### 2.7 Validation runtime and agent policy (user directive, 2026-09-29)

- **Container runtime:** OrbStack only, via Docker context `orbstack` (its data directory is on the external UGreen drive). Docker Desktop and the `default`/`desktop-linux` contexts are not used. Plan task 0.4 therefore measures cold and warm baselines on OrbStack only.
- **Real-LLM validation trials** use harness `codex-cli` with model `gpt-6-luna` (the `SupportedModelProfile` in `agents/adapters/codex_cli.py`, `low` only; not `gpt-5.6-luna`) at `reasoning_effort=low`. Public form: `make agent-smoke HARNESS=codex-cli PROVIDER=openai MODEL=gpt-6-luna`; agent-smoke defaults the effort to `low`. The Makefile takes provider and model separately, so there is no `codex/gpt-6-luna-low` spelling. No other harness or model is used for validation trials. Harbor `oracle`/`nop` agents are used wherever no real agent is needed.
- **Consequence for the 0.3 spike:** the plan names Claude Code, but under this policy the context-isolation check exercises the **`CODEX_HOME` reset in `setup.sh`**, not Harbor's `CLAUDE_CONFIG_DIR` wipe. Codex's reset recipe is therefore needed in Phase 0 rather than later (F11 ordering is unchanged for product coverage). Claude Code isolation stays unverified until a Claude trial is authorised.

## 3. Alternatives considered

### 3.1 Fallbacks (kept live until the 0.3 spike is green)

| Option | Mechanism | Why not chosen | When it is chosen |
|---|---|---|---|
| **E** | A custom Harbor agent that loops fresh `claude -p` calls inside one trial | Works on 0.1.42, but per-checkpoint results fall outside Harbor's result model, so Raidar re-implements step sequencing and artifacts | If A′ fails the verifier, reset or process-reap checks on the pinned version |
| **B** | One Harbor trial per checkpoint, chained by Raidar, oracle out of band, halt decision in Raidar | Strongest isolation, but about 8× the trial start cost for an 8-checkpoint problem [INFERENCE until 0.4 timings] | If A′ isolation cannot be made reliable. The choice between E and B uses the 0.4 overhead timings |

### 3.2 Superseded options (design-memo)

| Option | Source | Why superseded |
|---|---|---|
| Raidar owns the checkpoint loop; Harbor demoted to an optional backend; harness adapters retargeted to `SandboxBackend.exec` | design-memo §10.2 | Assumed Harbor could only verify inside the shared environment. A custom host-side `BaseVerifier` on ≥0.23 removes that constraint, and the loop would add bespoke code against N4 |
| `host-srt` (Seatbelt/bubblewrap) as the canonical sandbox with a synthetic HOME | design-memo §10.3, §10.6 | Harbor has no host backend, so it is the highest-risk build. Host-kernel boundary, macOS `sandbox-exec` deprecation, and read-deny gaps. Harbor's docker backend meets N2 |
| Harbor 0.1.42 with in-environment multi-step verification | design-memo §0, §10.2 | 0.1.42 has no `[[steps]]`. In-environment verification places tests in the agent's environment (leak class #1960) |
| Apple `container` backend | design-memo §5.1–5.2 | Needs macOS 26; the workstation is macOS 15 (N6). Revisit later |
| Pydantic Monty | design-memo §5.1 | Python-subset interpreter; cannot host an agent, a test suite or other runtimes |
| Scenario-attached weighted scorers | design-memo §1.2 | Scorers deciding success and applying weights; replaced by observation-only scorers plus ScorePolicies |

## 4. Consequences

**Positive**

- Harbor owns environment lifecycle, agent installation, step sequencing, artifacts, concurrency and the trajectory format. Raidar code shrinks to what N4 lists.
- Hidden tests stay host-side by construction, not by sandbox policy.
- One-shot and multi-checkpoint problems share one pipeline, config and scoring path (F1).
- SCB's Harbor dataset can be imported rather than re-authored (F13), subject to the 0.5 parity check.
- Offline regrading and rescoring work over stored per-step snapshots (F6, N3).

**Negative / risks**

- **Harbor API churn.** Mitigated by the exact pin and the spike-gated upgrade (§2.6).
- **Process reaping is Raidar's job** until Harbor PR #3454 lands. The per-step `setup.sh` is a regression-tested component (plan C3).
- **Porting cost.** Repo-local CLI agents must move to the ≥0.23 API (plan 0.2).
- **Harbor port vs native SCB grading** is unverified. Divergent problems are excluded (plan 0.5).
- **Harness coverage differs per step reset.** Each new harness needs its own state-reset recipe (e.g. `CODEX_HOME`, `CLAUDE_CONFIG_DIR`) and its own passing isolation check before it is admitted. Under §2.7 only the Codex recipe is validated in Phase 0.
- The scenario epoch becomes history. Comparisons across epochs are not supported.

**Follow-ups**

- Phase 0 exit requires: this ADR approved; Harbor pinned; the A′ spike green (or E/B chosen with timing evidence); N1 budgets set; at least one validated 8-checkpoint problem and one validated one-shot problem.

## Appendix A: Spike evidence

Evidence gathered in Phase 0 on 2026-09-29. Status of this ADR stays **Proposed** until the user approves it. Raw evidence lives in the files linked from each subsection; this appendix summarises it.

### A.1 Harbor pin and API port (plan 0.2)

- **Pin:** `harbor==0.23.0` in `orchestrator/pyproject.toml` and `orchestrator/uv.lock`. 0.23.0 is the latest stable on PyPI as of 2026-09-29; everything newer is a `0.23.1.devYYYYMMDD` pre-release. `orchestrator/.venv/bin/harbor --version` prints `0.23.0`.
- **Knock-on pins:** LiteLLM is now a direct exact pin, `litellm==1.102.1` (Harbor needs `>=1.92.0`; not 1.82.7/1.82.8). Harbor 0.23.0 needs Python ≥3.12, so `requires-python`, ruff `target-version` and mypy `python_version` moved from 3.11 to 3.12.
- **Install path:** Harbor is a project dependency installed by `uv sync`, no longer a global `uv tool install harbor`. `harbor_executable()` in `agents/adapters/base.py` resolves the venv binary, falling back to `harbor` on PATH.
- **CLI port:** `--agent-import-path X` → `--agent module:Class`; `--no-export-traces` dropped (removed in 0.23). Other flags unchanged.
- **Agent kwargs:** custom `__init__` kwargs replaced with pydantic `options_model` classes (`CliAgentOptions`, `ClaudeCodeCliAgentOptions` with `effort`/`thinking_mode`, `CodexCliAgentOptions` with `reasoning_effort`). Harbor rejects unknown `--ak` keys (`extra=forbid`).
- **Hooks / auth:** Raidar uses no Harbor hook events, so the hyphenated rename needed no change. Raidar's own credential mounting still works on 0.23.
- **Smoke:** `make agent-smoke HARNESS=codex-cli PROVIDER=openai MODEL=gpt-6-luna TIMEOUT_SEC=300` (effort `low`) ran on 0.23.0: exit 0, `execution_valid=True`, 54.7 s. **Caveat:** Raidar's host-side gates all exited 127 (`PosixPath('/app/None')`), so the composite 0.325 is not evidence that host scoring works. The same failure appears in pre-upgrade runs on 0.1.42, so it is not caused by the port; it is tracked separately.
- **Harbor 0.23 facts that bind the design:**
  - `verifier.import_path` and its kwargs are trial-level (`TrialConfig.verifier`), not `task.toml`; the execution layer must inject them.
  - Shared-mode steps require a `tests/test.sh` even with a custom verifier; importers emit a stub that is never uploaded.
  - The SCB converter's build smoke calls the removed `harbor task check` (0.23 uses `harbor check`).

### A.4 Overhead baseline and proposed N1 budgets (plan 0.4)
